================================================================================
 SOFTLY — CONFIG.TXT
 The coder's guide to every value that goes into `.env`
 Each step: WHAT it is -> WHERE to get it -> PRO TIP.
================================================================================

HOW TO USE THIS FILE
  1. Copy `.env.example` to `.env` (real secrets live ONLY in `.env`).
  2. Work through the sections below in order (Section 1 is mandatory).
  3. Restart the app after every change — Next.js caches env vars at boot.
  4. Verify with the checklist at the end.

SECURITY RULES (read once, follow forever)
  * `.env` is gitignored and chmod 600. Never commit it, never `git add -f .env`.
  * NEVER paste a connection string / API key / password into chat, GitHub
    issues, pull requests, screenshots, screen recordings, Discord, or a
    shared terminal (it lands in shell history + CI logs).
  * NEVER hardcode secrets in src/ "just to test" — always process.env.X.
  * NEVER run `drizzle-kit push --url="postgresql://..."` on the command line.
  * INCIDENT NOTE: a Neon password was pasted into chat earlier and was later
    rejected by the server (28P01 = invalid password) — it was rotated/stale.
    If you still see that string anywhere: rotate it in Neon now.

--------------------------------------------------------------------------------
 SECTION 1 — DATABASE (required; nothing else works without it)
--------------------------------------------------------------------------------

1.1  DATABASE_URL
     WHAT:   PostgreSQL connection string. Used by Drizzle (`src/db/index.ts`)
             and by `drizzle-kit` (see `drizzle.config.ts`).
     WHERE:  Neon console -> your project -> **Connect** tab. Two URLs are offered:
               - POOLED   (host contains `-pooler`)  -> for the APP on serverless
                                                        (Vercel / Cloudflare)
               - DIRECT   (host has no `-pooler`)    -> for `drizzle-kit push`,
                                                        migrations, and this
                                                        long-running preview
             Local sandbox alternative:
               postgresql://postgres:postgres@127.0.0.1:5432/app_db
     FORMAT: postgresql://USER:PASSWORD@HOST/DATABASE?sslmode=verify-full
     PRO TIP: always append `?sslmode=verify-full`. It verifies the server's TLS
              certificate and hostname (it also silences the pg SSL warning).
              `require`/`prefer` are weaker and will change behaviour in pg v9.

1.2  Rotating / activating Neon (do this when a URL is rejected)
     Symptom: `28P01 password authentication failed`  (the pasted URL is dead)
     Steps:
       1. Neon -> your project -> Roles -> neondb_owner -> Reset password.
       2. Connect -> copy the URL -> paste it into `.env` (DATABASE_URL only).
       3. Run `./scripts/db-setup.sh` — it checks connectivity, pushes the schema
          and lists all 19 tables WITHOUT printing your URL.
     PRO TIP: before any schema change, create a Neon **Branch** — that's an
              instant backup you can restore from if `push` does something
              unexpected (push can drop columns silently).

1.3  Applying schema (pick ONE workflow per environment)
       local/dev : `npx drizzle-kit push`            (interactive)
       CI/pipes  : `npx drizzle-kit push --force`    (auto-approves)
       production: `npx drizzle-kit generate` + `npx drizzle-kit migrate`
                   (versioned migration files committed to git)
     Pro: `drizzle.config.ts` loads dotenv itself, so NO `--url`, `--dialect`
          or `--schema` flags are ever required again.
     PRO TIP: never mix `push` and `migrate` on the same database — the
              migration history and the live schema will drift apart.

1.4  Checking tables
       ./scripts/db-setup.sh            (lists tables + row counts)
       psql "$DATABASE_URL" -c "\dt"    (never echo the URL itself)
       Neon -> SQL Editor               (visual)
     PRO TIP: the catalog seeds itself on the FIRST page request. If counts are
              0 right after `push`, start the app and load `/` once.

--------------------------------------------------------------------------------
 SECTION 2 — ACCESS & SECRETS (mandatory for production)
--------------------------------------------------------------------------------

2.1  ADMIN_EMAIL  /  ADMIN_PASSWORD
     WHAT:   Your private admin login for `/admin/login`.
             Setting BOTH disables the public preview admin automatically, and
             later edits to ADMIN_PASSWORD rotate the stored hash on restart.
     WHERE:  Invent them. ADMIN_EMAIL = a real mailbox you control.
             ADMIN_PASSWORD = a long random string (16+ chars).
             Generate one:  openssl rand -base64 24
     PRO TIP: read them from `.env`, not from chat — don't paste passwords into
              this guide, a README, or a screenshot. Change them after any
              handoff or staff change (edit `.env`, restart, done).

2.2  DOWNLOAD_SECRET
     WHAT:   Signs expiring guest download + online-reading links so they
             can't be guessed or forged.
     WHERE:  openssl rand -hex 32   (paste the output into `.env`)
     PRO TIP: set it once and keep it STABLE — changing it instantly invalidates
              every existing guest link (registered account holders are fine).
              Back it up in your password manager before rotating.

2.3  NEXT_PUBLIC_SITE_URL  /  SITE_URL
     WHAT:   The canonical HTTPS origin of your site. Used for password-reset +
             order emails, Stripe success/cancel redirects, sitemap.xml and
             robots.txt. NEXT_PUBLIC_* is also visible to the browser (expected
             here — it's public, not a secret).
     WHERE:  Your deployed domain, e.g. https://www.yourdomain.com
     PRO TIP: scheme + domain, NO trailing slash. A wrong value silently sends
              customers to `localhost` links in emails and Stripe redirects —
              set it BEFORE going live and test a password reset.

--------------------------------------------------------------------------------
 SECTION 3 — PAYMENTS (Stripe)
--------------------------------------------------------------------------------

3.1  STRIPE_SECRET_KEY
     WHAT:   Server-side secret that creates PaymentIntents/Checkout Sessions.
     WHERE:  dashboard.stripe.com -> Developers -> API keys -> "Reveal" secret key
             (sk_test_... in test mode, sk_live_... in live mode)
     PRO TIP: keep the account in TEST mode until your first successful
              end-to-end purchase; only then swap to sk_live_.

3.2  STRIPE_WEBHOOK_SECRET
     WHAT:   Verifies the digital signature of every Stripe webhook — this is
             what unlocks paid orders. Without it checkout returns 503.
     WHERE:  dashboard.stripe.com -> Developers -> Webhooks -> Add endpoint
               URL:  https://YOUR-DOMAIN/api/webhooks/stripe
             Events: payment_intent.succeeded, payment_intent.payment_failed,
                     checkout.session.completed,
                     checkout.session.async_payment_succeeded,
                     checkout.session.async_payment_failed, charge.refunded
             Then open the endpoint and copy the Signing secret (whsec_...).
     PRO TIP: the webhook secret is PER ENDPOINT (per domain + per mode). A local
              `stripe listen` secret will NOT validate live traffic — copy the
              exact one for the endpoint you created.

3.3  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY
     WHAT:   Loads Stripe.js + the on-page card form (cards, Apple Pay, Google
             Pay, Link). If empty, checkout falls back to Stripe's hosted page.
     WHERE:  Same API-keys page -> publishable key (pk_test_... / pk_live_...)
     PRO TIP: this key is safe to expose in the browser by design. Never put the
              *secret* key in a NEXT_PUBLIC_ variable — it would ship to users.

3.4  ENABLE_DEMO_CHECKOUT
     WHAT:   Set `false` to hard-disable preview checkout once payments are live.
             Empty/unset = demo mode ON automatically while no Stripe key exists.
     PRO TIP: deploy with it empty first; flip to `false` only after a real test
              charge succeeds, so customers never hit a dead checkout.

     The app will not accept real money until 3.1 + 3.2 (and ideally 3.3) are set.

--------------------------------------------------------------------------------
 SECTION 4 — EMAIL (Resend)
--------------------------------------------------------------------------------

4.1  RESEND_API_KEY
     WHAT:   Sends all transactional email: welcome, verify, password reset,
             order confirmation + secure link, refund notice, contact replies.
     WHERE:  resend.com -> free account -> API Keys -> create -> copy (re_...)
     PRO TIP: put it in `.env` only; it's a server-side secret. Revoke + reissue
              if it ever appears in a log or screenshot.

4.2  EMAIL_FROM
     WHAT:   The From header: "Your Brand <address@yourdomain.com>"
     WHERE:  resend.com -> Domains -> Add domain -> verify DNS (SPF + DKIM) ->
             then use an address on that domain, e.g. "Softly <hi@yourdomain.com>"
     PRO TIP: until your domain is verified, only `onboarding@resend.dev` works,
              and it may only send to your own account email — verify the domain
              BEFORE testing order emails, or messages silently fail to deliver.

     Without email, the store still works: customers use the secure link on the
     confirmation page; emails simply aren't sent (shown as "not configured").

--------------------------------------------------------------------------------
 SECTION 5 — PRIVATE FILE STORAGE (Cloudflare R2 / S3)
--------------------------------------------------------------------------------

     PDFs and uploaded images must NOT be public. These four values store them
     in private object storage and serve them through authorized routes.
     Without them, files go to local disk (fine for one persistent server,
     NOT for serverless — files disappear on redeploy).

5.1  R2_ENDPOINT
     WHAT:   The S3 API endpoint for your bucket.
     WHERE:  dash.cloudflare.com -> R2 -> create bucket -> Manage R2 API Token
             Endpoint looks like: https://<ACCOUNT_ID>.r2.cloudflarestorage.com
5.2  R2_ACCESS_KEY_ID       <- created with the R2 API token
5.3  R2_SECRET_ACCESS_KEY   <- shown ONCE at token creation; store it safely
5.4  R2_BUCKET              <- the bucket name you created (e.g. softly-files)
     PRO TIP: scope the API token to that ONE bucket with Object Read & Write
              only. Never issue an account-wide token. Region must be `auto`.

--------------------------------------------------------------------------------
 SECTION 6 — RUNTIME
--------------------------------------------------------------------------------

6.1  NODE_ENV
     WHAT:   `production` (set by the host), `development`, `test`.
     WHERE:  Usually unset locally; hosts set it automatically.
     PRO TIP: don't set it manually in `.env` — it changes cookie flags
              (session cookies become Secure) and Next.js build behaviour.
             Also controls whether session cookies are marked `Secure`.

--------------------------------------------------------------------------------
 HOW TO APPLY CHANGES
--------------------------------------------------------------------------------
   Local      : edit `.env`  -> restart (`npm run dev` / rebuild). Done.
   Vercel     : Project -> Settings -> Environment Variables -> add the SAME
                names for all three scopes: Production, Preview, Development.
                Local `.env` does NOT ship to Vercel.
   Secrets    : treat every value as secret except NEXT_PUBLIC_*.
   CI         : inject as environment variables; never write them into files
                that are checked in.

--------------------------------------------------------------------------------
 VERIFICATION CHECKLIST (run in order)
--------------------------------------------------------------------------------
   [ ] 1. `node -e "require('dotenv').config();console.log(!!process.env.DATABASE_URL)"`
          -> prints `true` (and never the URL itself)
   [ ] 2. `./scripts/db-setup.sh`
          -> "connected", tables (19), counts non-zero
   [ ] 3. `npx next typegen` && `npx tsc --noEmit`
          -> no output = clean
   [ ] 4. `npm run build` -> all routes compile
   [ ] 5. Start app, open `/` -> no `relation "..." does not exist`
   [ ] 6. `curl -s localhost:3000/api/health` -> {"ok":true}
   [ ] 7. `/admin/login` with ADMIN_EMAIL + ADMIN_PASSWORD -> dashboard loads
   [ ] 8. Admin -> Settings -> integrations: Stripe / Email / Storage as expected
   [ ] 9. Place a test order (preview mode) -> receipt + reader + PDF work

--------------------------------------------------------------------------------
 TROUBLESHOOTING — always read the stack trace BOTTOM-UP
--------------------------------------------------------------------------------
   28P01  password authentication failed  -> password rotated/wrong; reset it
          in Neon -> Roles, paste new URL into `.env`, rerun scripts/db-setup.sh
   3D000  database does not exist         -> wrong database name in the URL
   ETIMEDOUT / ENOTFOUND                  -> endpoint typo, or direct host used
                                             from serverless (use the -pooler host)
   "relation ... does not exist"          -> schema not pushed; run the setup
          script, then check the failing table name in the trace
   "url required" from drizzle-kit        -> `drizzle.config.ts` not being read;
          confirm the file exists and has `import "dotenv/config"` (no JSON config)
   Payment says "not configured"          -> 3.1 + 3.2 missing (3.3 for card form)
   Emails never arrive                    -> 4.1 missing or 4.2 domain unverified
   Uploads vanish after redeploy          -> Section 5 (R2) not configured
   Changed an env var, nothing happened   -> restart the server; env is cached
   404 on an image = asset path issue     500 = state/DB issue -> fix 500s first

--------------------------------------------------------------------------------
 NEVER DO
--------------------------------------------------------------------------------
   x Paste DATABASE_URL / API keys / passwords into chat, git, issues, screenshots
   x Commit `.env`, `.env.local`, or any file containing `npg_` / `sk_` / `re_`
   x Hardcode a connection string in src/db/index.ts
   x Put a secret in a NEXT_PUBLIC_ variable
   x Run `push` against production without a Neon branch/backup first
   x Mix `push` and `migrate` workflows on one database
   x Use the direct (non-pooled) Neon host inside serverless functions
   x Deploy to Vercel without setting the env vars there (local .env won't ship)
   x Use Vercel Hobby for a commercial store (against their ToS)
   x Ignore the pg SSL warning in production -> use sslmode=verify-full
   x Run the seed blindly in production (it won't overwrite edits, but check first)
